# Flow retrospective and role-bound repair

## Establish the execution lane

At entry, preserve the user's requested outcome and identify the role, object,
allowed writes and exclusions in the existing task/checkpoint. A flow
retrospective owns coordination evidence and authorized skills/working agreements;
its product findings do not turn it into an implementation Worker. Implement an
explicitly assigned source repair only in its implementation lane. Do not use
"complete end to end" to expand a Dispatcher or reviewer role.

For Studio, Importer or coordination-tool code findings, search the canonical
repository's open and closed Issues, existing PRs and live assignments first.
Compare the affected behavior, environment, phase and revision, not only titles.
Reuse a matching repair owner and add trace-bound evidence or a scope amendment.
Create a missing Issue only within issue-management authority; filing it does not
authorize a Worker launch. Already merged fixes are not new implementation work.
Distinguish symptom, failed condition, causal mechanism and root cause. A
reproduced failure or identified stage alone is not a root cause. Report
confirmed cause, ruled-out explanations and unknowns separately; state the next
discriminating check and a concrete repair/verification recommendation when
implementation lies outside this role.

Direct skills/AGENTS.md fixes use the versioned normative source. Do not edit an
installed snapshot, copy an old global skill over a repository skill, or rewrite
another owner's uncommitted tree. Separate source validation, commit, merge,
installation, session adoption and observed effect. Keep observations in the
existing evidence/checkpoint, not a new status ledger or maintained runbook.

## Skill binding across clients

Before launching a Worker, the assignment must name its role skill and project
profile, their canonical source/package identity and the permitted delivery scope.
Read the applicable skill and references; a skill name in a catalog or launcher
prompt is not proof that its instructions were loaded. Record the selected path
and revision/hash with the existing startup/checkpoint evidence, together with
native session, actor, reservation generation and actual runtime policy.

A Claude launcher, callback or process assumption is not a Codex capability.
Verify the effective client/model/permission mode and a supported callback route
before claiming readiness. A startup/provider failure is a runtime failure until
evidence shows a skill violation; preserve the same assignment/native identity
through supported recovery. Do not silently launch another Worker.

At resume, re-read the assignment, effective decisions, current phase references,
and custody/operation state. If a package changed, compare the applicable contract
and record adoption at a safe boundary; a link change does not load instructions
into an active session or transfer ownership. Do not repeatedly reload every
reference or resend the full assignment. A material scope amendment carries the
changed decision and its implications once, preserving unaffected work.

## Pause and unattended operation

A user's pause overrides ordinary persistence. Stop new mutations, dispatch,
review sampling and source delivery at a safe boundary. Preserve uncommitted work,
claims, reservations and external-operation evidence; pausing a turn never proves
an Action or database operation stopped. Do not reset protected locks, replace a
Worker, or terminate a shared backend. Check only the owned operations needed for
safe custody and record pending versus acknowledged pause accurately.

Before relying on unattended progress, verify the actual session/ledger/receiver
binding and the existing heartbeat's enabled state and target. Preserve explicit
pauses and one-controller ownership. Delivered, handled and completed are distinct
states. Unsupported App delivery or a paused/old-session heartbeat is a capability
gap to record and assign, not a reason to claim the Dispatcher will wake.

## Release findings

Keep release selection and environment ownership with the current Deployer.
A source/tool repair enters main after test/review, then the release owner selects
one exact new main head and audits the complete production delta, including extra
merges, configuration, migration, compatibility, recovery and downstream effects.
Prepare fresh candidate CI/images/provenance, staging acceptance and production
admission with a new immutable tag/manifest; retain old evidence and mark the old
candidate superseded only through the owner's transition. Once selected, pin the
SHA. Transient failures needing no source change retain the original candidate.

Detached-tag support stays compatible with in-flight releases. New default rules
never authorize another task to retarget an existing release. Runner maintenance
is separate infrastructure work and must not restart a busy deployment lane.
Correlate storage failures by exact environment, serving revision, route, time and
trace; a later staging error cannot explain an earlier production error alone.
